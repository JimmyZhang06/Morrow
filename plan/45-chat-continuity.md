# 聊天连续性与可控校验

## 这次解决的问题

原来回答流只是临时预览。供应商截断、正文 JSON 格式出错或附加字段校验失败时，即使已经收到文字，页面也会清空。另有 6,000 字正文上限，会拒收部分长回答。

本轮真实模型合成对话复测确实遇到 2 次格式失败：正文完整，但英文引号没有按 JSON 转义。没有使用用户原聊天记录。

## 已实施

- 普通聊天仅要求 `answer`。说明文字由程序提供默认值，标题仍可由模型可选生成，也保留原有问题摘要兜底及手动编辑。
- 标题、说明、关怀来信和引用列表分别规范化。无效的可选字段不拖垮正文；未知字段和工具指令仍受原有边界约束。
- 原文引用匹配与字符位置由程序计算。普通聊天隐藏不匹配的引用并保留正文；回信模式仍要求真实日记依据，不能把无依据的信伪装成有引用的信。
- 对答案优先输出的完整 JSON，程序可修复正文中未转义的英文引号，保留文字和可解析的附加字段。只处理可解析的完整边界，不补写缺失的正文、引用或括号。
- 已收到的截断正文经过当前材料和授权复核后加密保存，刷新后仍可阅读。它与完整回答使用不同的返回字段，不显示已验证引用，不触发关怀来信或认识生成。
- 后续上下文包含这段文字并明确标记为未完成、未验证的草稿。界面提供“接着说”，填入续聊问题；用户发送后继续，不自动重发原请求。
- 正文及预览上限由 6,000 字提高至 24,000 字。优先输出正文，并建议日常回复简洁，减少附加信息挤占输出。
- 供应商把最后一段文字与截断标志放在同一帧时，先保留文字；忽略流式请求而返回普通 JSON 的供应商也可以保留已收到正文。

## 验证

- 480 项 AI 与应用测试通过。覆盖字段默认值、长正文、引号与换行、截断最后一帧、加密保存、刷新读取、继续对话、材料变化及权限撤销。
- Ruff、Mypy、TypeScript 与 Vite 构建通过。
- 桌面回归通过：逐字显示、取消、中断后正文保留、页面刷新再打开、EOF 最后帧、明确截断、续聊时模型获得先前草稿。
- 两份真实格式失败响应在本地回放后可完整解析；最终另外连续 6 次真实模型调用均成功，耗时约 3.0–5.1 秒。这里验证的是模型传输与解析；桌面保存与续聊使用隔离档案和可重复的合成响应验证。
- 桌面截图：`.data/release-evidence/streaming/chat-preserved-answer.png`。
- 新版目录：`apps/desktop/release-chat-continuity/win-unpacked/`，保留整个目录运行。

## 边界

仍然保留结构化协议以支持已有引用和关怀功能，本轮没有把所有生成任务改为纯文本协议。完整性校验也不等于事实正确性。若没有收到正文、原材料或授权变化，不能展示未经授权的旧草稿；应用在保存前被强制结束的流式文字也不能保证恢复。用户的原数据、原模型配置和正在运行的旧程序未修改。
