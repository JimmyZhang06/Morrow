# 自我认知 Life Coach：前端 UI 设计交付与需求文档

版本：v0.1  
日期：2026-08-24  
面向角色：产品设计师、UI/UX 设计师、前端工程师  
当前阶段：核心闭环 MVP

---

## 1. 项目简介

这是一个帮助用户记录生活碎片、逐渐理解自己，并把认识转化为小行动的个人 Life Coach 产品。

产品不是“知道用户一切的 AI 聊天机器人”，也不是心理诊断工具。它更像一本会逐渐形成脉络、但始终允许用户纠正的私人生活笔记：

```text
记录一条生活碎片
  → 系统提出一个带原文证据的候选认识
  → 用户确认、纠正或暂不判断
  → 系统提出一个低压力的小行动
  → 用户接受、调整、撤销或完成后回顾
```

产品最重要的信任原则是：

1. 用户原话不能被 AI 静默修改。
2. AI 的解释必须明确标为“候选认识”，不能包装成事实。
3. 用户必须能看到解释来自哪些记录。
4. 用户的确认、纠正和撤销优先于 AI 判断。
5. 行动建议不是命令，不采用羞耻、催促或打卡惩罚设计。
6. 用户可以随时删除记录，并理解删除会影响哪些派生内容。

---

## 2. 本次设计目标

本次不设计完整“人生操作系统”，只完成一个可测试的用户闭环：

> 记录一条碎片 → 获得一个带证据的候选认识 → 确认或纠正 → 生成一个可撤销的小行动。

设计稿需要让团队验证三个问题：

1. 用户是否愿意低压力地持续记录？
2. 用户是否能够区分“自己的原话”和“AI 的推断”？
3. 候选认识是否能自然地转化为一个由用户自己决定的小行动？

首版成功不是“用户记录很多”，而是：

> 用户理解候选认识的依据，主动确认或纠正它，并自愿选择了一个小行动。

## 3. 目标用户与使用场景

### 3.1 目标用户

- 平时有零散想法，但不愿写长日记的人；
- 希望理解自己的情绪、选择、关系或工作模式的人；
- 使用过 Flomo、备忘录、日记或 AI 对话产品的人；
- 希望获得温和提醒，但反感被评判、说教和过度量化的人。

### 3.2 高频场景

- 通勤途中记下一句话；
- 一次会议、争执或决定之后记录感受；
- 睡前写下当天反复想到的事情；
- 回看近期记录，确认自己是否出现重复模式；
- 把一个模糊愿望转成明天可以尝试的小动作。

### 3.3 使用情境约束

- 用户可能只有 10～30 秒完成记录；
- 内容可能非常私人，界面需要有安全感而不是社交感；
- 用户可能处于疲惫、低落或困惑状态，操作不能复杂；
- AI 分析可能需要等待，不能用假进度制造确定性；
- 用户不应被迫立即回应每条候选认识。

## 4. MVP 范围

### 4.1 本次必须设计

- 首次进入与最小隐私说明；
- 首页/记录流；
- 快速记录编辑器；
- 记录详情和原始版本展示；
- 候选认识卡片；
- 证据原文展开层；
- 确认、纠正、驳回、稍后处理；
- 小行动候选；
- 调整、接受、完成、撤销行动；
- 最小通知中心或待处理入口；
- 隐私与删除确认；
- 加载、空状态、失败、离线和权限失效状态；
- 桌面端与移动端关键响应式稿。

### 4.2 本次不设计或只保留入口

- 完整回忆录编辑器；
- 人生主线可视化；
- 复杂人物关系图谱；
- Todoist、日历、邮件等外部连接；
- 社区、分享、关注和排行榜；
- 连续签到、积分、等级和人生评分；
- 心理疾病诊断或量表结果页；
- 多模型选择和高级 prompt 设置；
- 复杂数据分析 Dashboard。

未来功能可在信息架构中保留扩展空间，但不能干扰当前闭环。

## 5. 设计基调

### 5.1 三个关键词

**安静、可信、留白。**

界面应该像一个私人思考空间，而不是效率工具后台，也不是 AI 科技展示页。

### 5.2 视觉原则

1. **内容优先**：用户文字是页面视觉中心，装饰和数据指标退后。
2. **一次只做一件事**：每个页面最多有一个明确主操作。
3. **逐层展开**：证据、置信度、授权和版本信息默认收起，需要时再展开。
4. **原话与推断视觉分层**：二者必须使用稳定、可辨认的视觉语法。
5. **温暖但不幼稚**：避免医疗蓝、赛博紫、过度渐变和卡通化心理符号。
6. **克制使用卡片**：不要把所有内容都装进同样的圆角卡片；通过排版和留白建立层级。
7. **低刺激**：不使用红点轰炸、闪烁、强制弹窗和高压倒计时。
8. **真实状态**：AI 未完成时显示“正在整理”或“暂时无法生成”，不伪装成人类正在实时思考。

### 5.3 建议视觉方向

- 背景：偏暖的低对比中性色，而不是纯白大面积强光；
- 主文字：接近墨色，保证长文本阅读；
- 强调色：单一、低饱和，可选择鼠尾草绿、温和靛蓝或棕灰；
- 警示色：只用于真正需要注意的错误或安全信息；
- 圆角：中小圆角，避免所有模块“气泡化”；
- 阴影：尽量少，用边界、底色和留白代替；
- 字体：中文阅读优先，正文行高舒展；
- 动效：150～250ms 的轻微状态过渡，不使用庆祝撒花作为默认反馈。

设计师可以提出另一套视觉方向，但必须保留“安静、可信、留白”的体验目标。

## 6. 信息对象的视觉语法

这是本项目最重要的 UI 规则。不同信息不能混为同一种聊天气泡。

| 信息类型 | 用户应如何理解 | 建议视觉表达 |
|---|---|---|
| 原始记录 | “这是我当时写下的原话” | 正文排版；明确时间；不加 AI 口吻 |
| 候选认识 | “系统注意到的一种可能性” | 使用“也许/可能/我注意到”；标注待确认 |
| 证据片段 | “候选认识来自这些原话” | 引文样式；显示来源日期；可跳回原记录 |
| 反证/例外 | “并非所有记录都支持这个判断” | 与支持证据并列，而非隐藏在二级说明中 |
| 用户确认 | “这是我当前认可的理解” | 明确用户确认时间和可撤销状态 |
| 用户纠正 | “AI 的说法不准确，这是我的版本” | 用户文本优先；保留被纠正版本但默认收起 |
| 行动候选 | “一个可以尝试、但尚未承诺的建议” | 不使用任务完成框；强调可调整和跳过 |
| 已接受行动 | “这是我自己选择的小行动” | 才进入行动状态，可完成或撤销 |
| 安全提示 | “系统需要暂停普通分析并提供支持资源” | 清晰、平静、直接，不制造恐慌 |

设计稿必须能在不阅读说明文字的情况下，大致分辨“原话、AI 推断、用户确认、行动”四种对象。

## 7. 信息架构

MVP 建议只保留三个一级入口：

```text
记录
├─ 记录流
├─ 快速记录
└─ 记录详情

认识
├─ 待回应
├─ 已确认
└─ 已纠正/已驳回（低优先级历史）

行动
├─ 当前行动
├─ 待选择
└─ 已完成/已撤销
```

设置和隐私通过头像/菜单进入，不建议成为底部第四个高频入口。

移动端建议底部导航；桌面端建议窄侧栏。快速记录按钮可以作为持续可见的主操作，但不要遮挡正文。

## 8. 完整用户流程

### 8.1 首次进入

目标：建立信任，不做冗长问卷。

页面内容：

1. 一句话说明：记录越多，系统越能从片段中发现可能的模式。
2. 三条底线：AI 只提出候选、每条认识有来源、用户可纠正和删除。
3. 明确产品不是心理诊断或医疗服务。
4. 主按钮：“写下第一条”。
5. 次要入口：“先看看它如何工作”。

首版不要要求用户填写人格、人生目标、职业、年龄等完整画像。

### 8.2 快速记录

目标：10～30 秒内完成一条记录。

必要元素：

- 自动聚焦的多行输入区；
- 占位文案：“此刻有什么值得记下来？”；
- 保存按钮；
- 可选时间/标签入口，默认不展开；
- 本地草稿状态；
- 明确的私密提示，但不要反复制造隐私焦虑。

交互要求：

- 输入后离开页面不能静默丢失；
- 保存后优先回到记录流，不弹出强制分析结果；
- 允许只有一句话、无标签地保存；
- 自动分析是后台状态，不能阻塞保存；
- 如果离线，应先保存本地草稿并说明尚未同步。

### 8.3 记录流

目标：让用户感到“这是我的生活记录”，而不是 AI 消息列表。

每条记录显示：

- 正文前 3～6 行；
- 记录时间；
- 可选的轻量处理状态，如“已整理出 1 个候选认识”；
- 进入详情的点击区域。

禁止：

- 为每条记录展示复杂情绪分数；
- 默认显示人格标签；
- 无限堆叠 AI 总结；
- 用红点催促用户回应候选认识。

### 8.4 候选认识出现

候选认识可以在“认识”页出现，也可以在记录流中以克制的提示出现。

推荐卡片结构：

```text
一个可能的发现                         待你判断

“你似乎在需要公开表达意见时，更容易先否定自己的判断。”

来自 3 条记录 · 也发现 1 个例外

[看看依据]

[符合我的感受]  [不完全是]  [暂不判断]
```

文案要求：

- 使用可能性语言，不使用“你就是”“你总是”；
- 避免人格诊断、依恋类型、疾病标签；
- 不显示伪精确的 87% 置信度；
- 如需要表达可靠程度，使用“线索较少/有一些重复/多次出现”等自然语言。

### 8.5 查看依据

目标：帮助用户判断，而不是证明 AI 正确。

建议使用底部抽屉、侧边面板或独立详情页，内容包括：

- 支持该认识的原文片段；
- 每条片段的日期和来源；
- 点击回到完整记录；
- 反证、例外或不确定信息；
- 简短说明：“这些片段支持一种可能解释，但不代表完整的你。”

证据引用不得脱离上下文制造确定性。移动端应允许展开完整原记录。

### 8.6 确认、纠正与驳回

#### 确认

用户点击“符合我的感受”后：

- 显示轻量确认状态；
- 提示“这会成为你当前认可的一条认识，之后仍可修改”；
- 随后才可邀请用户查看小行动。

#### 纠正

用户点击“不完全是”后，不展示复杂表单，先提供三种轻量路径：

- “方向接近，但表达不准确”；
- “只在某些情境下如此”；
- “这不是我的情况”。

随后提供一个可选输入框：

> “如果由你来描述，更接近什么？”

用户的纠正文本成为主版本；AI 原版本进入历史记录，不与纠正版本并列争夺视觉权重。

#### 暂不判断

- 不等于拒绝；
- 可在未来出现新证据后再次呈现；
- 不应持续发送催促通知。

#### 驳回

- 允许用户明确选择“这不符合我”；
- 询问原因应为可选；
- 驳回后不要立即用换一种措辞重复同一判断。

### 8.7 生成小行动

只有在用户确认或完成纠正后，才出现行动候选。

行动需要满足：

- 5～20 分钟内可尝试；
- 描述具体，不是“变得更自信”；
- 不涉及自动联系他人、支付、公开发布或创建外部日历；
- 允许调整时间、难度和措辞；
- 有“现在不需要”的退出选项。

建议结构：

```text
要不要做一个很小的尝试？

下次会议前，先在备忘录里写下一句你真正想表达的观点。

大约 3 分钟 · 仅供尝试

[我愿意试试]  [调整一下]  [现在不需要]
```

接受前称为“行动候选”，接受后才称为“我的行动”。

### 8.8 行动状态

接受后的行动支持：

- 标记完成；
- 修改；
- 撤销；
- 稍后回顾；
- 说明实际发生了什么。

完成反馈避免夸张奖励，使用平静文案，例如：

> “已记下。之后可以看看，这次尝试有没有带来不同。”

未完成不使用红色、失败、逾期惩罚等表达。可使用“没有进行”“不再适合”“想换一种方式”。

## 10. 关键组件

设计师需要建立可复用组件，而不是逐页绘制孤立页面。

### 10.1 内容组件

- Source Record：原始记录；
- Source Quote：带日期和来源跳转的证据引文；
- Candidate Insight：候选认识；
- Counterevidence：反证/例外；
- Confirmed Insight：用户已确认认识；
- User Correction：用户纠正版本；
- Action Candidate：未接受的小行动；
- Accepted Action：已接受行动；
- Processing Status：后台整理状态。

### 10.2 操作组件

- 单一主按钮；
- 次要文字按钮；
- 三选一判断控件；
- 可撤销状态提示；
- 删除确认；
- 本地草稿/同步状态；
- 轻量 Toast；
- Bottom Sheet / Side Panel；
- 空状态和错误状态。

### 10.3 状态命名

用户界面不直接暴露后端枚举，但应保持语义一致：

| 技术状态 | 建议用户文案 |
|---|---|
| processing | 正在整理 |
| candidate | 等你判断 |
| confirmed | 你已确认 |
| corrected | 已按你的理解修正 |
| rejected | 你认为这不符合 |
| deferred | 暂不判断 |
| action_candidate | 一个可选的小尝试 |
| accepted | 你准备尝试 |
| completed | 已记下结果 |
| revoked | 已撤销 |
| failed | 暂时无法完成 |
| unknown | 结果尚未确认 |

## 11. 全局状态设计

每个 P0 页面至少提供以下状态稿：

1. 正常有数据；
2. 首次空状态；
3. 加载状态；
4. 后台处理状态；
5. 可恢复失败；
6. 权限或授权失效；
7. 内容已删除；
8. 离线或同步未完成；
9. 多次点击/重复提交后的幂等反馈；
10. 移动端窄屏状态。

### 11.1 加载状态

- 记录保存与 AI 分析必须分开；
- 保存成功后不应因 AI 尚未完成而继续阻塞；
- 骨架屏只用于结构稳定的区域；
- 超过合理等待时间后，提供离开页面的选择。

### 11.2 失败状态

- 不展示 provider、数据库或内部策略错误正文；
- 使用稳定的用户文案和“稍后重试”；
- 不把分析失败描述为用户内容有问题；
- 如果授权失效，应说明需要重新确认哪类用途。

### 11.3 删除状态

删除确认至少需要解释：

- 原始记录将不再显示；
- 依赖该记录的候选认识可能失效或被撤回；
- 已确认认识若失去全部证据，应标为来源已删除，而不是继续伪装成有证据；
- 后台彻底擦除可能需要时间；
- 删除账户与删除单条记录是两个不同操作。

## 12. 文案与语气规范

### 12.1 推荐语气

- “我注意到一种可能……”
- “这与你的感受符合吗？”
- “这些记录提供了一些线索。”
- “也有一条记录不完全符合这个模式。”
- “如果由你来描述，更接近什么？”
- “要不要尝试一个很小的动作？”
- “现在不需要也没关系。”

### 12.2 禁止语气

- “系统判定你是……”
- “你的真实人格是……”
- “你总是/你从不……”
- “你必须面对……”
- “检测到你患有……”
- “完成今天的任务才能保持进度。”
- “你已经连续失败 3 天。”

### 12.3 AI 身份表达

不建议让 AI 扮演一个拥有强人格、持续拟人化注视用户的角色。首版可使用“系统”“我注意到”或中性产品名称，但必须保持：

- 不声称拥有感受；
- 不暗示替代朋友、咨询师或医生；
- 不使用依赖诱导文案；
- 不制造“只有我真正懂你”的关系。

---

## 13. 心理安全要求

本产品是自我反思工具，不做临床诊断。

设计中禁止：

- 把短期状态固化为稳定人格标签；
- 通过颜色或分数展示“心理健康等级”；
- 对用户进行道德评价；
- 在高风险表达后继续推送普通效率建议；
- 自动联系家人、医生、警方或第三方；
- 用危机资源弹窗覆盖所有模糊负面表达。

如果安全系统触发高风险状态，页面应：

1. 使用平静、直接、非诊断的语言；
2. 暂停普通候选认识和行动推荐；
3. 提供所在地适用的即时支持资源；
4. 建议联系可信赖的人或专业帮助；
5. 明确系统不能提供紧急救援；
6. 不自动执行外部联系。

安全支持页的最终文案需要产品、法律和专业心理人员共同审核，UI 设计稿只能提供结构与占位文案。

---

## 14. 隐私设计要求

- 默认私密，不出现公开分享入口；
- 敏感内容不能出现在系统通知预览中；
- 列表页避免在未解锁场景暴露完整正文，可预留隐私遮罩模式；
- 用户能理解 AI 分析需要使用哪些记录；
- 每条候选认识可查看来源；
- 授权变更必须使用人能理解的目的描述，而不是只有法律条款；
- 删除和撤销入口不能藏在多层菜单；
- 不使用“为了更懂你，请开放全部权限”一类诱导文案；
- 不展示假的“端到端加密”承诺。

建议在候选认识的证据面板中加入轻量说明：

> “本次整理使用了 3 条记录。你可以查看具体来源，或删除不希望继续使用的内容。”

## 15. 响应式与可访问性

### 15.1 目标尺寸

- 移动端优先：375px 和 430px；
- 桌面端：1440px；
- 中间尺寸需说明布局折叠规则；
- 长文本、中文换行和系统字体放大必须纳入设计。

### 15.2 可访问性要求

- 正文和关键操作达到 WCAG AA 对比度；
- 不只使用颜色表达状态；
- 点击区域建议不小于 44×44px；
- 支持键盘导航和清晰焦点状态；
- 表单有可读 label，不只依赖 placeholder；
- 动效支持减少动态效果设置；
- 屏幕阅读器能区分原始记录、候选认识和用户确认状态；
- 错误提示与对应输入关联；
- 证据抽屉打开后正确管理焦点。

---

## 16. 与后端能力的边界

当前后端已经具备部分领域模型和安全边界，但完整业务 API 尚未全部接通。设计时请遵循以下原则：

1. 可以设计完整 MVP 体验，但不要假设所有接口已经可用。
2. 对未实现能力标注 `API pending`，不要用纯前端假逻辑掩盖。
3. AI 分析、删除和外部操作都需要异步状态。
4. 候选认识、用户判断、行动候选必须是不同实体和不同状态。
5. 原始记录修改应体现“新修订”，不能假设覆盖原始历史。
6. UI 不直接决定 consent、证据有效性或模型状态；以后端权威状态为准。

建议设计稿的开发标注至少包含：

- 页面依赖的实体；
- 空/加载/失败状态；
- 主操作及幂等行为；
- 是否需要异步刷新；
- 删除或撤销后的页面变化；
- 需要后端补充的字段。

## 18. 设计验收标准

设计稿只有同时满足以下条件才算完成：

- 用户可以在 30 秒内完成一条无标签记录；
- 页面能明确区分原话、AI 推断、用户确认和行动；
- 每条候选认识都存在可发现的“查看依据”入口；
- 用户能确认、纠正、驳回和暂不判断；
- 行动候选不会自动变成任务；
- 用户能撤销已接受行动；
- 删除入口可发现，并解释对派生内容的影响；
- 所有 P0 页面包含空、加载和失败状态；
- 不使用诊断、评分、羞耻或依赖诱导设计；
- 移动端单手操作可行；
- 关键颜色和交互达到基础可访问性要求；
- UI 没有以聊天窗口承载全部产品对象；
- 首屏没有堆叠统计图、复杂导航和多个竞争主按钮。

## 19. 第一轮可用性测试任务

高保真原型完成后，建议让测试用户完成以下任务：

1. 写下一条刚刚发生的小事；
2. 找到系统从记录中提出的一条可能认识；
3. 查看该认识使用了哪些原文；
4. 表达“方向接近，但只在工作场景如此”；
5. 把系统建议的小行动改得更容易；
6. 接受行动后再撤销；
7. 删除一条记录，并说明自己认为哪些内容会受到影响。

观察指标：

- 是否把候选认识误认为事实；
- 是否能找到证据入口；
- 是否理解“纠正”和“驳回”的区别；
- 是否认为行动是被强迫接受的；
- 是否相信删除真的会生效；
- 哪些文案让用户感到被评判或被监视；
- 完成核心路径所需时间和返回次数。

## 20. 待产品与设计共同确认的问题

这些问题不阻塞第一轮线框，但高保真定稿前需要明确：

1. 产品名称、Logo 和正式品牌色；
2. 候选认识出现的最低证据数量；
3. “暂不判断”何时允许再次呈现；
4. 是否需要应用锁或敏感内容遮罩；
5. 删除记录后，已确认认识采用撤回、降级还是“来源已删除”状态；
6. 行动是否允许设置站内提醒；
7. 首版是否支持语音记录和图片附件；
8. 安全支持资源首发地区；
9. 中文之外的首发语言；
10. 桌面 Web 与移动 Web/PWA 的首发优先级。

在这些问题确定前，设计稿应使用可替换 token、组件和占位文案，避免把尚未决策的产品规则固化进视觉结构。
